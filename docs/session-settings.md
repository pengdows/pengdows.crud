# Session Settings Enforcement

pengdows.crud applies dialect-specific session-settings scripts **after** it knows which dialect it is talking to and **only if** the dialect provides non-empty SQL. The policy is "Always SET" (`SqlDialect.BuildSessionSettingsScript`): the script carries every expected setting and is sent on every checkout, with no check of the current value first. A pooled connection may have been changed by an earlier caller, and sending the settings costs less than reading them to decide (measured on SQLite: about 1 µs per extra setting in one command, against +31 to +50 µs for a query that reads them).

## Key guarantees

- Dialect detection completes during `DatabaseContext` initialization (`DatabaseContext.Initialization.cs`), flipping `_sessionSettingsDetectionCompleted`. Any physical connection opened before that flag would block is now a no-op for session SQL.
- Every `TrackedConnection` runs the `onFirstOpen` callback on its first `Open`, but the callback now checks `DataContext.SessionSettingsPreamble` and returns early when there are no statements to execute (`DatabaseContext.ConnectionLifecycle.cs`).
- The script runs once per `TrackedConnection` wrapper, not once per physical connection. Persistent modes (`SingleConnection`) keep one wrapper for the context's lifetime, so the script runs once. Ephemeral modes (`Standard`, `SingleWriter`) create a wrapper per operation, so the script runs on every checkout, even when the provider's pool hands back an already-open physical connection. That is deliberate: it re-establishes the session invariants whatever the previous user of the connection did (`StickySessionSettingsTests`). On SQLite it means one command per operation, `PRAGMA foreign_keys = ON; PRAGMA query_only = OFF;`, plus `PRAGMA synchronous = NORMAL;` once the database is known to be in WAL mode (the context reads the journal mode right after it sets WAL, and builds the settings again if it changed); see `docs/connection/connection-modes.md`, section 4. Both are per-connection settings that Microsoft.Data.Sqlite's pool would otherwise carry from one checkout to the next: a caller that turns foreign keys off, or `query_only` on, through a container cannot leave it that way for the next operation (`SqliteQueryOnlySessionTests`). `query_only` is only ever put OFF: SQLite refuses `BEGIN IMMEDIATE` on a `query_only` connection, which would stop a read transaction beginning, so read-only is `Mode=ReadOnly` in the connection string instead.

## Tests that guard the behavior

1. `MySqlSessionSettingsTests.SessionSettingsAppliedWhenStandardConnectionOpens` – ensures the first Standard-mode connection executes the MySQL SQL mode commands after the dialect has been detected (`pengdows.crud.Tests/MySqlSessionSettingsTests.cs:76-94`).
2. `SessionSettingsEnforcementTests.DatabaseContext_AppliesSessionSettingsAfterDialectDetection` – confirms at least one connection received a dialect-generated `SET` command, indicating the callback still fires for a real dialect post-detection (`pengdows.crud.Tests/SessionSettingsEnforcementTests.cs:66-100`).
3. `SessionSettingsEnforcementTests.SessionSettingsSkippedWhenDialectProvidesNoStatements` – uses DuckDB (no session script) to ensure no `EXECUTE NONQUERY` calls happen when the dialect explicitly reports “nothing to do” (`pengdows.crud.Tests/SessionSettingsEnforcementTests.cs:82-105`).
4. `SessionSettingsApplicationTests.StandardMode_InitializesSessionSettings_ForAnsiQuotes` – kept to verify `SessionSettingsPreamble` still exposes the ANSI_QUOTES snippet for MySQL/MariaDB, so documentation and tests stay in sync.

If anyone changes `DatabaseContext` to touch `_sessionSettingsDetectionCompleted`, `ConnectionLocalState.SessionSettingsApplied`, or `ApplyConnectionSessionSettings`, rerun these tests and make sure this document still reflects the story before merging.
