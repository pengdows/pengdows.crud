Three small, well-contained P1 items were found still genuinely open at the baseline, fixed with
TDD, verified against the full unit suite (8314/8314 green on net8.0 and net10.0), and pushed:

- **DateTimeOffset/UTC normalization family-check** — closed in `dd2e994`. Replaced the hardcoded
  `SupportedDatabase` enum-family switch in `SqlDialect.CreateDbParameter` with a real capability,
  `NormalizeDateTimeOffsetToUtc` (declared once on `PostgreSqlDialect`/`MySqlDialect`, inherited
  by every wire-compatible family member). **This surfaced two live bugs the switch had been
  silently missing**: `AuroraPostgreSql` and `SingleStore` were never getting DateTimeOffset
  values normalized to UTC, because both are plain `PostgreSqlDialect`/`MySqlDialect` instances
  constructed with a different `DatabaseType` tag (`SqlDialectFactory.CreateDialectForType`), not
  subclasses — exactly the failure mode the review predicted for this pattern.
- **SQL Server generated-key protocol out of generic `TableGateway`** — closed in `e074547`. The
  `dialect is SqlServerDialect` check in `TableGateway.Core.cs` (building the OUTPUT-into-a-
  table-variable workaround for tables with triggers) moved entirely into `SqlServerDialect` via
  a new `IInternalSqlDialect.RenderOutputInsertClauses` hook — internal-only, no public API
  surface change. No behavior change; verified against the existing 33-test characterization
  suite plus 2 new dialect-level tests.
- **Singleton gateway `AuditCreationPolicy` immutability** — closed in `6f01a9a`. Changed from
  `{ get; set; }` to `{ get; init; }` on `ITableGateway`/`IPrimaryKeyTableGateway` and the
  concrete `BaseTableGateway<TEntity>` implementation. Source-breaking for anyone setting it
  post-construction (zero such call sites exist in this repo today; the only existing usage was
  already object-initializer syntax, which `init` supports unchanged). Verified via a
  reflection-based test asserting the CLR's `IsExternalInit` modreq is actually present, not just
  trusting the C# keyword.

All other items below remain open and are sized for Codex's broader pass — several (the P0
ReadWriteMode audit, provider identity separation, the vendor-branch audit, the cache-semantics
audit) are genuinely audit-shaped work, not small fixes, and weren't attempted in this session.

## The standard this review is held to

This is the conclusion the user reached partway through drafting the backlog below, and it
supersedes the framing of the individual line items where they conflict — read this first:

> The goal is not merely "move vendor checks into the dialect." The goal is: **everything below
> `IDatabaseContext` absorbs database/provider differences so completely that ordinary consuming
> code cannot tell which supported database is underneath.**

The application should never have to say things like:

```csharp
if (context.Product == SupportedDatabase.Sqlite) ...
if (dialect.SupportsReturning) ...
if (database.RequiresSingleWriter) ...
if (provider.UsesPositionalParameters) ...
if (serverVersion < ...) ...
```

Nor should it have to configure those differences:

```csharp
options.UseSingleWriter = true;
options.UseLegacyMySqlUpsert = true;
options.NormalizeOracleTimestamps = true;
options.UseOutputInserted = true;
```

That is all pengdows.crud's problem.

**Five rules this tightens the mandate to:**

1. **No database feature knowledge may escape upward.** If a caller needs to know that
   PostgreSQL has RETURNING, SQL Server has OUTPUT, SQLite needs writer serialization, OLE DB
   binds positionally, Oracle handles some temporal type differently, or MySQL syntax changed at
   8.0.20, that is abstraction leakage. pengdows.crud detects it and does the right thing.
2. **Capabilities are internal implementation facts, not application configuration.**
   Internally it is fine for a dialect to have concepts like `GeneratedKeyStrategy`,
   `JoinParenthesization`, parameter-binding semantics, supported paging syntax, or
   server-version-dependent behavior. The normal user should never query those capabilities to
   decide what to do.
   - BAD: `Application → asks SupportsX → pengdows.crud → Database` (the application becomes
     part of the compatibility layer).
   - GOOD: `Application → asks for operation → pengdows.crud determines required semantics →
     chooses implementation → Database`.
   - The public abstraction should express **intent**, not mechanism: `Execute(...)`,
     `Insert(...)`, `Update(...)`, `Retrieve(...)`, `BeginTransaction(...)`, `ExecutionType.Read`,
     `ExecutionType.Write`, `ReadWriteMode.ReadOnly` are legitimate. `SupportsOutputClause`,
     `NeedsWriterSerialization`, `UsesQuestionMarkParameters`, `RequiresReturningInto`,
     `MySqlPre8020` belong underneath the abstraction.
   - Even `DbMode.SingleWriter` should generally be pengdows.crud's own conclusion about the
     database, not something ordinary application code has to understand to function.
3. **Same application operation, different internal execution is the success condition.** This
   is why the MySQL 8.0.19/8.0.33 singleton-gateway test matters: it proves *same gateway, same
   call, same entity, same application semantics → different internal SQL per live server
   capability → same correct result*. Apply that test philosophy everywhere — e.g. "insert and
   obtain generated key" should route through RETURNING/OUTPUT/Oracle's mechanism/SQLite's
   mechanism/MySQL's mechanism with the caller never having a reason to know which happened;
   "execute concurrent writes" should route through real concurrent writers, internal SQLite
   serialization, or FlatFile's constraints with the same caller code either way.
4. **Unsupported must mean semantic impossibility, not missing adaptation.** If database A has
   the necessary semantics but spells/implements them differently, pengdows.crud adapts. If
   database B fundamentally cannot provide the semantic contract a higher-level operation
   requires, pengdows.crud rejects the operation/database combination — that isn't abstraction
   leakage. E.g. a Hangfire caller should never write `if (db == Snowflake) DontUseHangfire();`;
   instead, constructing Hangfire storage against an unsuitable context should fail immediately
   and clearly ("This database cannot satisfy the transactional/locking semantics required by
   pengdows Hangfire storage") — a semantic boundary, not a dialect leak.

**The revised audit instruction, verbatim:**

> Audit pengdows.crud for every place where a consumer could be required to understand database,
> provider, dialect, server-version, concurrency, parameter-binding, connection-lifetime,
> generated-key, temporal, transaction, or SQL-syntax differences. Eliminate that requirement.
> Move detection and adaptation below the `IDatabaseContext`/dialect/provider boundary.
> Supported databases must present one coherent application-facing behavioral contract. Do not
> expose feature flags merely to make callers branch around differences. A database-specific
> condition is acceptable internally; requiring consuming code to know about it is a defect.

**The acceptance test to apply everywhere:**

> For every public API operation, ask: could I write the consuming code without knowing what
> database this is? If the answer is no for any supported database, identify why and close the
> leak.

Not merely a provider-neutral API. Not even merely dialect-neutral SQL plumbing. The target is
**database-mechanics immunity above the pengdows.crud boundary.** This is also why
`pengdows.hangfire` is a useful architecture test: if a complex system like Hangfire can be
written once without saying "if SQLite… if PostgreSQL… if Firebird…", the abstraction is doing
its job.

## Backlog items

- **[P1] Move DateTimeOffset/UTC normalization out of database-enum family checks.** Re-verify
  whether generic DTO/materialization/binding code still decides UTC normalization using
  lists/switches of `SupportedDatabase` values. If so, replace that with a dialect/provider
  semantic capability inherited at the appropriate compatibility root, e.g.
  `NormalizeDateTimeOffsetToUtc`. Do not scatter new booleans through the code. **Acceptance:**
  PostgreSQL-family/MySQL-family behavior remains correct; unrelated providers are unchanged; one
  process can simultaneously use different normalization semantics without shared-state leakage.

- **[P1] Separate provider registration identity, provider invariant identity, and database
  product identity.** `ProviderName` must not ambiguously mean all three of: configuration
  lookup key, ADO.NET factory/invariant name, and detected RDBMS. Introduce/clarify concepts
  equivalent to `ProviderRegistrationKey`, `ProviderInvariantName`, and `Product`/dialect. This
  is now important because real Pengdows applications dynamically load providers and choose them
  per tenant. CMS, for example, can use a configuration key that resolves an independently
  registered factory. **Acceptance:** registration key may differ from invariant; diagnostics
  distinguish all identities; dialect detection is independent of registration spelling.

- **[P1] Move the complete SQL Server generated-key protocol out of generic `TableGateway`.**
  Re-check the historical concrete `SqlServerDialect` test/table-variable/OUTPUT machinery.
  Generic gateway code should ask the dialect/provider layer to implement the generated-key
  operation; it should not understand SQL Server's protocol. Do not replace the entire
  generated-key system with a strategy-object framework merely for cleanliness. **Acceptance:**
  no concrete SQL Server type/product check in generic gateway code; single-row and batch
  generated-key behavior stays identical.

- **[P1] Make singleton gateway policy immutable.** Re-check `AuditCreationPolicy`. If a
  singleton `TableGateway` still exposes something equivalent to public `{ get; set; }`, make it
  constructor-time/init-time immutable or otherwise incapable of request-time mutation. Do not
  solve this by making gateways scoped — Wiki and CMS prove that long-lived shared gateways with
  request-specific contexts are intentional architecture; CMS explicitly constructs singleton
  gateways against a bootstrap context and passes the real tenant context per call.
  **Acceptance:** two tenants/requests cannot change one another's gateway policy.

- **[P0 if any bypass exists] Exhaustively prove `ReadWriteMode.ReadOnly` really means incapable
  of writing.** The old partial-application defect was fixed, but the ecosystem has raised the
  importance of this contract: CMS uses `ReadWriteMode.ReadOnly` as part of its security boundary
  and forcibly applies it to every configured tenant. Audit every path that can produce a write:
  insert, update, delete, upsert, batch/bulk variants, raw `SqlContainer` write execution,
  generated-key variants, transaction APIs, retry contexts, direct `ExecutionType.Write`, and
  explicit write-connection acquisition. **Acceptance:** a test for every path proves rejection
  occurs before any provider write command executes. If even one bypass exists, treat it as a
  release blocker.

- **[P1] Guarantee that an explicit per-call context always dominates the gateway's
  bootstrap/default context.** This deserves a dedicated audit now. Wiki and CMS intentionally
  use a constructor context only to construct/cache the singleton gateway; the actual operation
  supplies its tenant `IDatabaseContext`. Audit helpers for quoting, paging, dialect selection,
  parameters, generated keys, connection selection, transaction use, server-version behavior,
  execution, and mapping. No operation that received context B may later consult context from
  bootstrap tenant A. **Acceptance:** construct gateway on tenant/provider A, execute against B,
  and prove every observable decision and DB operation uses B.

- **[P1] Audit every cache according to its real semantic identity.** Do not assume static caches
  are bad. Instead inventory SQL-plan, reader-plan, mapping, identifier, parameter, capability
  and generated-SQL caches. Document what inputs can change their result: dialect, server
  version, provider binding rules, table/schema identity, etc. Make each key contain exactly
  those dependencies. **Acceptance:** alternate and concurrently execute one singleton gateway
  across differing contexts without one context's compiled behavior contaminating another.

- **[P1] Extend the existing server-version isolation proof to provider-family isolation.** The
  MySQL 8.0.19/8.0.33 singleton-gateway test is excellent because it proves one gateway can
  simultaneously generate different SQL according to live server capabilities. Add at least one
  analogous test involving genuinely different provider/dialect families. The point is not "all
  DBs produce identical SQL"; it is "one shared application abstraction safely selects the right
  semantics for each context."

- **[P1/P2] Audit vendor/product branches above the dialect/provider boundary.** Search generic
  CRUD code for `SupportedDatabase.X`, concrete dialect type checks, `context.Product ==`, and
  equivalent switches. Do not mechanically delete all of them. For each, ask whether it
  represents a vendor SQL/provider semantic. If yes, move that semantic under the dialect/
  provider layer. If it represents legitimate orchestration/policy, leave it. The goal is
  semantic ownership, not zero product checks.

- **[P2] Treat session settings as a first-class lifecycle contract and prove it.**
  PostgreSQL-oriented consumers benefit substantially from pengdows.crud applying session
  behavior transparently. Verify that settings are applied whenever a new physical connection
  needs them, survive the intended transaction/session lifecycle, are reapplied after reconnect
  where required, apply appropriately to read/write pools, and don't bleed between tenant
  contexts. Include `PreventDatabaseUnload`/sentinel connections if they participate. This is
  validation first; don't redesign working machinery.

- **[P1/P2] Re-prove `DbMode`, `SingleWriter`, and `PoolGovernor` as application-visible
  guarantees.** No strategy-hierarchy rewrite. Verify: `SingleWriter` databases serialize the
  writes that require it; full servers aren't unnecessarily serialized; read-only operations
  don't consume write capacity; pinned transactions own/release permits correctly;
  cancellations/timeouts/provider exceptions cannot leak permits; queue/fairness invariants
  remain intact; and shared consumers such as Hangfire don't bypass governance.

- **[P2, potentially P1 if Access/OLE DB lands in 3.0] Cleanly separate provider transport from
  database dialect in dynamic provider loading.** Native `DbProviderFactory` loading is core
  architecture. Unknown providers may be dynamically loaded, and unknown products may reasonably
  fall back to SQL-92 only when the provider's binding semantics make that safe. OLE DB is the
  canonical exception: `OleDbFactory` is transport, not database identity, and positional `?`
  parameters mean an unknown OLE DB target must not silently take the ordinary SQL-92 fallback.
  Recognized SQL-Server-over-OLE-DB should be rejectable with "use SqlClient"; Access-over-OLE-DB
  can be a legitimate supported combination.

- **[P2] Improve diagnostics around dynamic database identity.** When a context is
  diagnosed/logged, make it possible to distinguish tenant/application context, provider
  registration key, ADO.NET provider/factory identity, detected RDBMS, detected server version,
  dialect, `DbMode`, and `ReadWriteMode`. This becomes important once one process can host
  radically different tenant databases. Don't turn this into verbose logging everywhere; make
  the information available at the right diagnostic boundary.

- **[P2] Use semantic capabilities, not product genealogy flags.** Where a behavior really
  varies, give it a semantic name such as `NormalizeDateTimeOffsetToUtc`,
  `JoinParenthesization.Required/Optional/Prohibited`, or an appropriate generated-key behavior.
  Avoid speculative forests of `SupportsX` flags and avoid names such as `IsMySqlLike` where the
  actual issue is one specific syntax/semantic. Add capabilities when observed behavior requires
  them.

- **[Guardrail] Do not "correct" dialect inheritance according to corporate ancestry.** Dialect
  inheritance means active compatibility contract, not genealogy. In particular, do not
  resurrect `SybaseDialect : SqlServerDialect`. MariaDB/TiDB inheriting MySQL behavior and
  Cockroach/Yugabyte inheriting PostgreSQL behavior can be correct where the used surface is
  intentionally compatible. If behavior diverges, override/split at that behavior — not because
  one product is historically unrelated.

- **[Wiki follow-up] Remove application-level vendor encoding once CRUD/SQL has the necessary
  semantic hooks.** `pengdows.wiki` currently has at least the PostgreSQL `ILIKE` choice in
  `PageGateway`; that is useful consumer feedback about a semantic operation CRUD/pengdows.sql
  could own. Replace literal vendor choices such as that — and any remaining literal `LIMIT 1`
  where dialect paging is appropriate — only after there is a clean semantic layer underneath. Do
  not make Wiki "portable" by reducing it to lowest-common-denominator SQL.

- **[Wiki follow-up] Add an actual heterogeneous-tenant smoke test.** One Wiki API process, one
  singleton gateway/service graph, at least two tenants backed by different database families.
  Prove routing, paging, quoting, parameter binding and generated SQL remain tenant-specific.
  Keep PostgreSQL as the preferred/optimized default; the test is proving optionality, not
  declaring all engines equivalent.

- **[CMS P1] Fail closed for an unknown production tenant/host.** CMS's own security review
  identifies the current default-tenant fallback as residual risk. Unknown/misconfigured public
  hostnames should not silently receive some other tenant's site. Provide an explicit
  development/default behavior if useful, but production multi-tenant resolution should be
  capable of rejecting unknown hosts. Add tests for unknown host, malformed tenant
  header/query selection, and cross-tenant leakage.

- **[CMS follow-up] Preserve defense-in-depth around read-only rather than weakening it.** Keep
  forced pengdows ReadOnly, SELECT-only production credentials, lack of mutation GraphQL, and
  the ability to make SQLite physically read-only. Don't add write conveniences to the public
  stack. The CMS security thesis is capability removal; any future write feature belongs on a
  separately trusted surface.

- **[Hangfire proof] Keep workload capability rejection legitimate.** Do not try to make
  Hangfire run on every database merely because CRUD can connect to it. Snowflake-like systems
  that don't satisfy Hangfire's transactional/locking/low-latency mutation requirements should
  remain rejected. Re-run/extend the matrix that proves the exact same Hangfire implementation
  works on supported full-server and SingleWriter targets.

- **[FlatFile/fakeDb proof] Protect alternative execution models as first-class consumers.**
  Ensure changes above do not assume a conventional server database. Run fakeDb
  failure-injection tests and FlatFile/SQLite SingleWriter tests. Provider failure, disposal
  failure and cancellation must still release connection/governor resources. Standard SQL
  execution and inspectable file-backed testing should remain possible without special
  application code.

- **[ETL proof] Validate long-lived transactional/concurrency behavior against the same core
  contracts.** Ensure ETL worker throttling, transaction ownership, transient retry, and
  SingleWriter limits continue to go through the normal pengdows mechanisms. Do not create a
  separate ETL-specific connection-management architecture to work around changes in CRUD.

- **[P2] Preserve SQL as the application's relational language.** When fixing vendor leaks, move
  vendor encoding underneath the application; do not replace explicit SQL with an ORM-like
  expression/query abstraction. Future pengdows.sql work should parse/preserve semantics and
  lower to vendor SQL, not use regex/string replacement. The Firebird natural-key move from
  string replacement to a dialect hook is the pattern to continue.

- **[Release gate] Run the ecosystem as an architectural acceptance suite before declaring 3.0
  ready.** At minimum: complete CRUD unit tests on all supported target frameworks; complete
  real-provider integration matrix; mixed server-version singleton test; mixed-provider
  singleton test; exhaustive ReadOnly write-denial suite; SQL Server generated-key tests;
  DateTimeOffset/provider-semantic tests; provider-key/invariant/product identity tests;
  session-setting and governor lifecycle tests; Hangfire integration suite; Wiki tests plus
  heterogeneous-provider smoke; CMS tests plus unknown-host fail-closed test; fakeDb/FlatFile
  tests; and a public API diff/freeze review. Anything expected to skip must be documented as
  expected rather than disappearing into a green count.

## Do-not-fix list

Equally important — Codex should **not**:

- Make gateways request-scoped.
- Narrow `IDatabaseContext` merely because it looks broad.
- Replace `DbMode` with a strategy hierarchy.
- Reorganize dialect inheritance by vendor family tree.
- Declare static caches inherently wrong.
- Reintroduce the reverted PGC008 widening (see `future-work.md` FEAT-016).
- Hide SQL behind an ORM abstraction.
- Revive previously withdrawn findings without new evidence.

## Final rule

> After these semantic ownership and contract issues are resolved, stop broad architecture
> surgery. Freeze the 3.0 API and prove the release.
>
> The ecosystem has changed the conclusion of the review. pengdows.crud no longer needs to prove
> that its unusual architecture is theoretically defensible. Hangfire, Wiki, CMS, FlatFile/fakeDb
> and ETL are already exercising it from materially different directions. The remaining job is to
> make sure the implementation never violates the architecture those consumers now depend on.
